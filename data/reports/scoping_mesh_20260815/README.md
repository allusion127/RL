## 1. 방법

### 1.1 셀 정의
`e_core 목표 ∈ {5.0, 5.2, 5.4, 5.6, 5.8, 6.0}` × `feed ∈ {105, 109, 113, 117, 121}`
= 30 셀. `feed = 4·N + 1`, N = 신연료 오빗 단위 수 (26…30).

### 1.2 연료쌍 선정 (50/50 분할)
`lpopt.data.fuel_types.FuelLibrary.pair_e_core(a, b, 0.5, lib)` — 추출/추론이 공유하는
U질량 가중 평균 농축도 레시피 — 로 **전 라이브러리의 full-physics 타입쌍**을 열거하고,
목표 e_core에 가장 가까운 쌍을 고른다.

* `feature_poor` 타입 제외 (격자 물리 피처가 없어 모델이 결측 센티널로 featurize 함).
  → ga80의 C(6.0)/D(6.5) 앵커는 **전부 feature_poor라 사용 불가**.
* 농축도 스프레드 `|e_a − e_b| ≤ 0.25` (스토어 `e_split` 99퍼센타일 0.166 기준,
  그 이상은 분포 밖 연료조합).
* paramA는 같은 격자가 **서술형 id와 짧은 레지스트리 별칭 두 이름으로 중복 등재**되어
  있어(`S7` == `P6257Z1G10N12`) 서술형만 열거한다. 그렇지 않으면 같은 물리 쌍이 네 가지
  철자로 나오고 "타입 + 자기 별칭"이 스프레드 0의 가짜 쌍으로 잡힌다.
* 동률 규칙: `round(|Δe_core|, 2)` → 스프레드 오름차순 → 해당 쌍의 스토어 행 수 내림차순.

### 1.3 후보 풀
셀마다 `lpopt.search.construct.build_pool` (캠페인 최적화기가 쓰는 바로 그 생성기)로
**2 웨이브 1,200 후보**:

* 웨이브 0 — 800개. 엘리트 부모 = ① 같은 라이브러리·`|Δe_core| ≤ 0.05` 밴드에서
  feed 거리 → F_r 순으로 정렬한 최평탄 노심 16개, ② 같은 밴드의 **가용(feasible)** 행 중
  cyclen 최대 16개 (없으면 cyclen 최대), ③ 스토어 전체에서 F_r이 가장 낮은 검증-가용
  노심 12개를 `fr_transfer.pair_mapping` + `substitute`로 이 셀의 쌍에 **배치 이름만
  재매핑**해 이식. `build_pool`이 목표 feed로 feed-morph 한다.
* 웨이브 1 — 400개. 웨이브 0의 최고 가용 후보를 `prev_top`으로, F_r이 한계 바로 위인
  후보를 `near_miss_parents`(n_moves = 1 신뢰영역)로 넣어 가용 경계를 좁게 탐침.
* 웨이브 0의 record_id를 웨이브 1의 ledger로 넘겨 중복 제거.

### 1.4 e_core 밴드 스크린
게놈의 배치 flip 이동이 50/50 분할을 흔들기 때문에
`construct.screen_e_core_band(..., tol = 0.02)`로 쌍의 50/50 e_core에서 ±0.02 안에
있는 후보만 셀의 대표로 인정한다. ga80 쌍은 두 타입의 농축도가 같아 항상 정확히
목표값이고, paramA 쌍만 실제로 걸러진다 (`n_in_band` 열 참조).

### 1.5 가용성 게이트 (예측 평균값)
`F_r ≤ 1.55` · `F_q ≤ 2.41` · `CBC_max ≤ 1600 ppm` · `|AO| ≤ 0.30`
— `lpopt.config`의 프로젝트 한계값(CBC는 lat1600 게이트 1600).
**노드 = 게이트를 통과한 후보 중 예측 cyclen 최대**. 그 후보의 예측 F_r과 앙상블
epistemic σ_cyclen을 함께 기록한다. 통과 후보가 0인 셀은 그림에서 **결측(구멍)**으로
두고 CSV에 `n_feasible = 0`과 진단값(`min_pred_f_r`, `max_pred_cyclen_any`)을 남긴다.

### 1.6 방출연소도 (y축) — 모델 헤드가 아니라 평형 질량수지

```
B_cycle [GWd/tU] = cyclen [d] × P_th [MW] / M_HM [tU] / 1000      P_th = 3983 MW
B_d     [GWd/tU] = B_cycle × 241 / feed
```

`M_HM`은 `data/store/fuel_types.parquet`의 쌍 평균 `u_mass_g`에서 나온다. 다만
DeCART 격자 출력의 `MASS(g) TOTAL`은 **단위길이·1/8 대칭섹터당** U 질량이라
FA 절대질량이 아니다. 환산계수는 스토어에서 실측했다 —
`P·cyclen/(1000·cycle_burnup)`을 `241 × 쌍평균 u_mass_g`로 나눈 값이
MASTER 라벨 38,854행에서 **3048.6 ± 1**, 즉 `8 섹터 × 381 cm 활성길이 = 3048`과
0.02% 일치한다. 따라서

```
FA당 U질량 [tU] = u_mass_g × 8 × 381 / 1e6          (≈ 0.422 – 0.424 tU/FA)
M_HM            = 241 × FA당 U질량                  (≈ 101.7 – 102.2 tU)
```

**검증**: 이 공식으로 계산한 `B_d`는 스토어의 MASTER 실측 `discharge_burnup`
38,220행을 상대오차 **평균 −0.002%, 표준편차 0.11%, 최대 0.57%**로 재현한다.

> `lpopt/design/coredeck.py`의 선언 상수 `hm_mtu = 104.8`은 MASTER가 실제로 쓰는
> 질량보다 **2.7% 높다** (실측 ≈ 102.0 tU). 여기서는 실측값을 쓴다.
> ga80 문자 라이브러리는 `u_mass_g`가 전부 NaN이라 모집단 평균
> `u_mass_g = 138.9`(FA당 0.4234 tU, M_HM 102.03 tU)를 적용했다 —
> 타입 간 편차는 ±0.5% 수준이다.

### 1.7 지지도 / 외삽 표기
그림의 채운 ● = feed 121, 빈 ○ = feed ≠ 121. CSV에는 셀별로
`n_store_feed` (같은 feed 전체), `n_store_feed_ecore` (같은 feed + `|Δe_core| ≤ 0.05`),
`n_store_feed_lib`, `n_store_pair_feed`를 담았다.

e_core 6.0 / feed 121이면 **796 EFPD · B_d 61.8 GWd/tU**까지 반응도가 있다.

가용 노드에서 feed를 121 → 117로 줄이면 주기는 짧아지지만(640 → 619 EFPD)

e5.2에서도 51.09 → 51.85로 0.8 GWd/tU만 움직인다. 즉 이 평면에서
**등농축 선은 거의 수평이고, B_d를 올리는 유일한 레버는 농축도다.**

## 4. 한계 · 주의

1. **모델 예측 전용.** 어떤 노드도 MASTER로 검증하지 않았다. s1e 챔피언의 재현도는

   CBC MAE 8.4 ppm) 이는 **분포 내** 성능이고, 낮은 feed와 높은 e_core 셀은 외삽이다.
2. **라이브러리 전환.** e_core 5.0/5.2/5.4는 ga80(문자 라이브러리), 5.6/5.8/6.0은
   paramA다. 어떤 full-physics 라이브러리도 5.0–6.0을 혼자 덮지 못한다 —
   ga80 full-physics 타입의 최대 농축도는 5.5, paramA는 4.74–6.37이지만 저농축 쪽
   스토어 지지가 얇다. 등장전량(회색) 선은 5.4↔5.6 구간에서 라이브러리 경계를
   가로지르므로 그 구간의 기울기는 연료 라이브러리 효과와 섞여 있다.
3. **MASTER 실현성.** ga80 쌍 E1_E2 / K1_K2 / N1_N2는 `FEASIBLE_PACKAGE/bases`에
   네이티브 재시동이 있다. 선정된 paramA 쌍 3개는 `data/design/package/bases`에
   (P0_P1, Q1_Q2, Q7_Q8, T3_T4, T5_T6, T6_T4만 존재) **재시동 베이스가 없어**
   MASTER로 확인하려면 먼저 `design bootstrap`이 필요하다.
4. **"feed 121 = 분포 내"는 스토어 전체 기준의 근사.** 스토어 72,685행 중 43,634행이
   feed 121이지만 그 대부분은 260624 / 5.8_5.1 라이브러리다. 이 스터디가 쓰는
   ga80·paramA 부분모집단은 오히려 feed 97–141에 넓게 퍼져 있다 (ga80 feed 121은
   3,454행으로 전체의 25%). 즉 **빈 마커(feed ≠ 121)가 반드시 지지 없는 외삽은
   아니다** — 실제 지지도는 CSV의 `n_store_feed_lib` / `n_store_feed_ecore`로 읽어야
   한다. 반대로 feed 105·113은 ga80에서도 287 / 460행뿐이라 얇다.
5. **후보 풀은 캠페인 예산의 일부.** 실제 캠페인은 셀당 pool_size 20,000 + local
   search를 돌린다. 여기서는 셀당 1,200이므로 각 노드는 그 셀의 **하한**이고,
   `n_feasible = 0`은 "이 예산으로 못 찾았다"이지 "존재하지 않는다"가 아니다.
   다만 e_core ≥ 5.6 셀은 최소 F_r이 게이트에서 0.17 이상 떨어져 있고 스토어의
   MASTER 실측(1 820 + 616행, 가용 0행)과도 일치하므로, 예산 문제로 보기 어렵다.
6. **분할은 50/50 고정.** 홀수/비대칭 분할은 스코프에서 제외했다.
7. **paramA e_core 5.3–5.7 구간은 스토어 지지가 0이다.** 5.6 셀(`n_store_feed_ecore`
   = 0)은 라이브러리 안에서도 완전한 외삽이라 다른 셀보다 신뢰도가 낮다.

### 9.0 주기길이 목표는 어디에도 없다 (검증 완료)

> **주기길이 목표 없음 — 안전인자 만족 하 주기길이·방출연소도 최대화.**

사용자 지시에 따라 코드 경로를 전수 확인했다.

| 확인 대상 | 결과 |
|---|---|
| 가용성 게이트 `_feasible_mask` | `F_r ≤ 1.55` · `F_q ≤ 2.41` · `CBC ≤ 1600` · `\|AO\| ≤ 0.30` — **cyclen 항 없음** |
| 노드 선택 | 게이트 통과 후보 중 `argmax(예측 cyclen)` — **최대화**, 목표·밴드 없음 |
| 셀 y축 `B_d` | cyclen의 단조증가 함수(질량수지) → 셀 안에서 방출연소도도 동시 최대화 |
| `lpopt.inp`의 `[acquisition] cycle_target_efpd = 625.0` / `cycle_tolerance_efpd = 2.0` | **이 경로에서 죽은 값.** 이 키를 읽는 곳은 `search/campaign.py`, `search/acquisition.py`, `report/report.py`, `vendor/masterrl/*` 뿐이고 그물망은 그중 무엇도 임포트하지 않는다 (`sys.modules` 확인: campaign·acquisition 모두 `False`) |
| `construct.build_pool` | `cfg.search`(풀 크기·비율·이동수)와 `cfg.acquisition`의 `policy_prior*`만 읽는다. `policy_prior`는 기본 `"off"`이고 덱에 없으므로 스코어러 자체가 로드되지 않는다 |
| `construct._score_completions` | **독스트링이 낡았다** — "predicted cyclen near the target"이라 써 있지만 실제 코드는 `F_r + F_q`만 더한다. 게다가 그물망은 `build_pool(ctx, None, …)`로 **model=None**을 넘기므로 이 함수는 즉시 `completions[:beam]`을 반환하고 채점 자체를 하지 않는다 |
| `build_elites` / `donors` | 밴드행은 (feed거리, `f_r`) 오름차순, 가용행은 `cyclen` **내림차순**, 도너는 최저 `f_r` — 전부 최대화/최소화이지 목표값이 아니다 |

**직접 증거**: s1f 노드의 예측 주기길이는 623.8–680.5 EFPD로 625±2 밴드를 한참 벗어나고,
제약 미적용 상한 열(`max_pred_cyclen_any`)은 575.6–796.4 EFPD에 걸쳐 있다.
목표가 걸려 있었다면 불가능한 분포다.

**한계(생성기는 재구축하지 않음)**: 엘리트 부모는 스토어에서 오고, ga80 가용행 991개 중
**78.3 %가 620–645 EFPD 구간에 몰려 있다** (실제 도너 24개는 631.6–638.6 EFPD).
이는 게이트가 아니라 `F_r ≤ 1.55` 자체가 좁은 주기길이 띠를 선택한 결과이며
(625±2 안은 0.3 %뿐 — 목표에 고정된 코퍼스가 아니다), 그래도 후보 풀이 그 띠 주변
패턴의 변이로 만들어진다는 사실은 남는다. **저장전량 셀의 미발견을 해석할 때 감안할 것.**

### 10.1 단일 최적 → Pareto 대표점

셀마다 argmax 하나로 접던 것을 그만두고, **안전인자만 만족하는 후보 집합 전체에서
(주기길이 최대, F_r 최소) Pareto 전선**을 뽑는다. 지배 판정은
"자기보다 주기도 길고 F_r도 낮은 후보가 있으면 탈락"이다. 게이트는 그대로다 —
바뀐 것은 **"가용 집합 안에서 무엇을 최적이라 부를지"를 코드가 정하지 않는다**는 점뿐이다.

`mesh_pareto.csv` — 8개 가용셀의 전선 **75점 전부**
(`cell`, `rank`, `rep`, `pred_cyclen`, `pred_f_r`, `pred_f_q`, `pred_cbc_max`,
`pred_ao_abs`, `pred_max_pin_bu`, `B_cycle`, `B_d`, `cand_e_core`, `record_id`, `origin`).
`rep` 열이 세 대표점을 표시한다 — `min_f_r`(최저 F_r) · `knee`(무릎, 7셀에서 검출) ·
`max_cyclen`(최장주기 = 종전 노드, 연속성 유지).

저장전량 영역에 국지적으로 나타났다** — 100행짜리 단일 셀 증분에서 기대할 수 있는
바로 그 모양이다.

### 11.7 실행 기록

199호기 24코어. s1g는 11샤드 × 2스레드로 시작했으나 **메모리 병목**이었고
(워커당 4.8 GB × 11 = 53 GB / 63.8 GB, 커밋 99.5 %, CPU 59 %에서 정체),
대조군부터는 **6샤드 × 4스레드**(29.8 GB, CPU ~100 %)로 바꿨다. 대조군 55셀
벽시계 **36분**. 샤드 오류 0건. `PASS_s1f.log`의 `failed_shards=6`은
`Start-Process -PassThru` 객체의 `ExitCode`가 null로 읽힌 **오탐**이다 —
6샤드 전부 정상 행수(10·10·10·10·10·5 = 55)를 썼고 `.err`는 전부 비어 있다.
