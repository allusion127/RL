## 1. Why this run exists

The 2026-08-16 campaign at this cell (`fpcamp_minfr_N1N2_f113_199.inp`,
results `data/reports/fpcamp_N1N2_f113_results_20260816.md`) reported 41
F_r-feasible cores under the objective's four legacy gates (F_r/CBC/F_q/|AO|)
and headlined a winner at **F_r 1.4961 @ 641.635 EFPD**. `min_fr_max_cycle`
gated nothing on pin burnup at that time — the knob
`[acquisition] minfr_pin_bu_limit` (config.py:280, default 78.0) landed
2026-08-17, one day after the campaign closed. That addendum (results doc
§7a) predicted all 41 cores breach 80 GWd/tU. The 2026-08-20 measured wave
(`data/reports/pinbu_wave_results_20260820.md`) confirmed it on real MASTER
chains: the winner measures **86.189 GWd/tU — FAIL**, and 0/5 spot-checked
top cores from this cell pass. **The F_r record stands; it was never
deliverable.**

This re-campaign runs the SAME cell with the pin gate now active
(`minfr_pin_bu_limit = 78.0`), current champion, fresh seed, budget 60.

## 3. Elite seeding — what is and is not wired in, and why

The cell's own campaign output (41 native f113 rows + 26 cross-feed f121/f125
rows from the 2026-08-16 run = 67 converged feasible N1_N2 rows) is seeded
**automatically**, no deck knob: `_case_store_rows` filters by `case_pair`
only, no feed filter, unchanged since 2026-08-16.

`elite_seed_cases = ["E1_E2"]` (the brief's suggested "proven knob") was
**investigated and left unset**. The precedent it is drawn from
(`fpcamp_minfr_HGD569_f125_SEEDCTL_199.inp` /
`fpcamp_minfr_TRIPLE_f125_199.inp`) donates a pair whose fuel-type alphabet is
a literal SUBSET of the target case's alphabet (2-type donor into a 3-type
target that already contains both donor types). E1_E2 → N1_N2 is a
**disjoint** alphabet swap — no shared type. Traced through the current code
(`genome.py:249,356`, `construct.py:140,264`): a donor pattern's non-delta
fresh positions keep their ORIGINAL batch label; `_morph_feed` only relabels
the feed-count delta to `ctx.batches`. Because ga80 is one shared 80-type
library, a mixed N1/N2/E1/E2 core would very likely resolve without error and
get written to the store MISLABELLED as `case_pair = "N1_N2"` — a data-
integrity risk with no tested precedent in this program. Full reasoning is in
the deck header (section "ELITE SEEDING").

This is registered as a **documented, deliberate omission**, not an
oversight — the readout in §6 below (basin-shift verdict) will show whether
its absence mattered, since the operative lever is the acquisition-time
pin-UCB penalty on every scored candidate (`acquisition.py:464-524`), not
elite-parent cleanliness. `is_feasible` treats a missing `max_pin_burnup` as
PASS by explicit contract, so elite ranking itself is unaffected by the new
gate either way — 34/41 of the cell's own elites carry no pin label and would
rank identically with or without the donor.

## 5. Success / partial / null

* **PRIMARY** — a MASTER-verified core at this cell that is BOTH F_r-feasible
  (≤1.55) AND passes the pin gate on its own predicted value (i.e. the
  campaign's own `state.json → best` is populated under the 5-gate
  definition). Zero such row exists today.
* **SECONDARY** — that core's F_r beats or matches the DB truth 1.5374, i.e.
  the search finds a loading pattern at least as good as the DB's own
  pin-clean core, not merely a pin-clean core at any F_r.
* **PARTIAL** — no 5-gate-feasible core, but the frontier under the pin
  constraint moves (i.e. the best predicted-pin-screened candidate's F_r
  falls meaningfully below 1.55, or the joint Pareto front records a
  materially lower minimum F_r among low-pin candidates than the 41-row
  legacy population).
* **NULL** — the search stalls without a single 5-gate-feasible core in 60
  calls. The honest reading is NOT that the cell is closed (the DB proves a
  73.30-pin, 1.5374-F_r core exists) — it is that **current 2-type ga80
  designs at this cell cannot jointly satisfy pure-F_r-minimisation and the
  pin margin in one 60-call search**, and the DB's core (split 0.540,
  N1×61/N2×52) was never re-derivable by this program's shuffle search even
  before the pin gate (the 2026-08-16 campaign's own winner sat at a
  different split, 0.681). That reading would hand the cell to a 3-type/
  graded design or a fuel-design lever, not to a bigger search budget alone.

## 6. Registered readouts (to be filled by the results doc, not before)

1. **Best F_r among predicted-pin ≤78 cores** (the campaign's own screened
   population), compared against 1.5374 (DB) and 1.4961 (old, pin-failed
   winner).
2. **Joint 5-gate feasible count** — how many of the ≤60 converged cores pass
   F_r/CBC/F_q/|AO|/pin-BU together, versus the parent campaign's 41 (4-gate)
   and 0 (5-gate, retroactively).
3. **Basin-shift verdict** — whether the new winner's loading pattern differs
   materially from the old winner's (Hamming distance on the canonical
   pattern, split ratio N1:N2, restart provenance) — i.e. whether the pin
   gate steers the search to a genuinely different region, or whether it
   simply fails to find anything and the search sits in the same basin the
   old winner came from.
4. **NULL reading**, if triggered: "pin-feasible frontier at this cell is
   above 1.55" — stated exactly as in §5, not softened.

Recommendation registered in advance, regardless of outcome: **any winner
this campaign reports needs an independent MASTER pin-burnup re-verification
(5-core spot check, same protocol as `pinbu_wave.py`) before a delivery
claim** — this campaign's own MASTER path does not measure pin burnup
(`enable_pin_burnup` is not exposed to `lpopt optimize`), so every result
below is a PREDICTED-pin-screened result, not a measured one, exactly like
the parent campaign's F_r result needed a measured wave before it could be
called FAIL. This run finds the recommendation candidate; it does not run
the verification.
