## 2. The reporting-layer gap this run exposes — read in full

`min_fr_max_cycle`'s pin screen (`score_min_fr_max_cycle`,
`acquisition.py:464-524`) penalises a candidate's **predicted** pin-burnup
UCB against `minfr_pin_bu_limit=78.0` at the moment it competes for a MASTER
slot. It is real and it does something (§4 shows a genuine basin shift for
at least one candidate). But it is **acquisition-time only**. Once a
candidate is sent to MASTER and verified:

* `lpopt optimize` does not measure pin burnup — `enable_pin_burnup` is not
  exposed on this path (confirmed unchanged from the parent campaign's own
  finding, results doc §7a). Every converged row in this run carries
  `max_pin_burnup = null`, exactly like the parent campaign's 98/98.
* `is_feasible()` (`campaign.py:263`) treats a missing `max_pin_burnup` as
  **PASS**, by explicit 2026-07-31 contract, so that elites/best-tracking are
  not starved by an unmeasured axis.
* Consequence: **`state.json → best_overall` selects the lowest-F_r row
  among 4-gate-feasible rows, with ZERO effective pin discrimination**,
  because the axis that would discriminate is never populated. The
  acquisition screened candidates BEFORE sending them to MASTER, but the
  bookkeeping that decides "best" afterward cannot see what was screened.

This was checked empirically, not inferred from reading the code alone. All
59 converged rows were re-scored against **the validated static s1i
checkpoint** (`data/models/s1i`, unmodified — the same artefact
`pinbu_wave_results_20260820.md` measured against 41 real MASTER chains,
POOLED bias −0.32/MAE 1.02), using `pinbu_wave.py`'s own `_score()` function
verbatim (the proven serve path — reproduced the known measured/predicted
pair for the OLD winner exactly: predicted 86.10 vs the 2026-08-20 measured
86.189, error 0.09):

| record | F_r | predicted pin (s1i, validated) | reads as |
|---|---:|---:|---|
| `c9bc21e9513b` (OLD winner, 2026-08-16) | 1.4961 | 86.10 | matches measured 86.189 — confirms methodology |
| `2bd607967f09` (this run's `best_overall`) | 1.4653 | **86.05** | same basin as the OLD winner (Hamming 15/69) — **NOT pin-screened in any meaningful sense** |
| `2ad9de110b1d` (this run's honest best, §3) | 1.5074 | **77.09** (UCB 78.89) | the only row that clears the gate on a point estimate |

The per-wave online finetune (a genuine, new lever versus the parent
campaign) is NOT the explanation for the `best_overall` gap — the
checkpoints it produces are what the acquisition used to RANK candidates for
MASTER dispatch, and clearly did admit `2bd607967f09` despite the base
model's ~86 reading (most likely: the wave-3 pool's pin-feasible mass was
thin and the "least-infeasible-first" fallback in `score_min_fr_max_cycle`
admitted the best-F_r candidate anyway, exactly as the code's own docstring
warns it will: *"no starvation before the first feasible label — which,
empirically at this cell, may never arrive"*). The gap is in the
**post-verification bookkeeping**, not the acquisition math, and it is the
same class of defect the parent campaign's results doc flagged in its own
§7.1 (`lpopt report`'s table not showing the true F_r winner) — a second,
more consequential instance of "trust `state.json`'s own labels at your
peril" for this objective.
